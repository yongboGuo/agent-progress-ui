# AI 长任务加载动画方案

## 1. 背景与目标

当 AI 任务从“秒级回答”进入“分钟级后台执行”后，用户最容易出现三种感受：

1. **不知道系统是不是还活着**；
2. **不知道 AI 到底在做什么**；
3. **不知道自己现在应该等待、干预，还是离开页面**。

所以，这类加载设计的目标不只是“好看”，而是要同时解决：

- **活性证明**：用户能持续感知 AI 仍在工作；
- **过程透明**：用户知道当前阶段、已完成内容、下一步方向；
- **可控感**：用户可以中断、调整、转后台、回来继续；
- **信任感**：用户看到的是“真实进度证据”，不是空转的 spinner；
- **焦虑抑制**：减少“页面卡死了”“任务丢了”“是不是要重新点一次”的误判。

---

## 2. 主流 AI 产品的可借鉴模式

下面只看“长任务 / 后台任务 / 多步骤任务”相关模式，不看普通聊天气泡。

### 2.1 ChatGPT

可借鉴点：

- **先出计划，再开始执行**：用户先看 proposed research plan，可修改后再开跑。
- **执行中可见进度，可中断**：任务运行时可以 follow progress，也可以中途 refine / interrupt。
- **长任务与短任务分层**：OpenAI 现在把快问快答和 Deep Research / Agent 区分得很清楚，说明不同时长任务需要不同反馈机制。
- **任务跨度被明确告知**：Agent 官方说明里直接写明很多任务通常需要 **5–30 分钟**，用户从一开始就知道这不是秒回场景。

启发：

- 长任务一定要**前置预期管理**；
- 不要只有“思考中”，而要给出**任务计划、当前阶段、可打断入口**；
- 任务越长，越需要从“加载动画”升级为“任务管理 UI”。

### 2.2 Gemini

可借鉴点：

- **研究前允许编辑计划**；
- **允许离开当前聊天**，结果好了再回来；
- **完成后主动通知**，网页线程和移动端通知都给到；
- **并发额度可见**，接近额度时会提醒用户。

启发：

- 对 5–10 分钟类任务，最关键的不是做更炫的动画，而是明确告诉用户：**你现在可以离开，任务不会丢**；
- “通知 + 线程标记完成”比持续播放大动画更有效；
- 后台任务必须有**恢复入口**，而不是把结果埋在旧会话里。

### 2.3 Perplexity

可借鉴点：

- **Deep Research 明确告诉用户任务不是瞬时完成**，而是会进行 dozens of searches、reads hundreds of sources；
- **任务模式切换明显**：普通搜索、Deep Research、Labs 不是一套反馈 UI；
- **Labs 强调 10 分钟以上的自监督工作**，已经不是“loading”，而是“项目执行”。

启发：

- 一旦 AI 开始做大量搜索、阅读、代码执行、图表生成，就不应继续使用“单一转圈”；
- 必须切到**项目态 / 工作态视图**，让用户感觉像在看一个任务被推进，而不是看一个网页在等待响应；
- 适合显示：来源数、工具数、已生成产物、可导出结果。

### 2.4 Claude / Claude Code

可借鉴点：

- **extended thinking 对用户可见**；
- Claude Code 在 IDE 里提供 **real-time sidebar + inline diffs**；
- 官方明确强化了 **status visibility**；
- 对更长任务提供 **checkpoints**、**subagents**、**background tasks**。

启发：

- 对高复杂度任务，用户需要的不只是“AI 正在想”，而是**AI 改了什么、做到哪一步、出了问题能不能回退**；
- 如果任务有风险或耗时长，应该给出**检查点 / 最近成功步骤 / 可回退状态**；
- “可见证据”优先于“抽象动画”。

### 2.5 GitHub Copilot Cloud Agent

可借鉴点：

- 提供统一的 **agents panel**；
- 会显示 **status、token usage、session length、session log**；
- 可 **steer、stop、archive**；
- 能并发跑多个 sessions。

启发：

- 当任务进入后台后，必须有一个**任务中心**；
- 用户不仅想看“正在执行”，还想看：**跑了多久、在做什么、消耗了什么、能不能中途改方向**；
- 对 agent 类产品，最有效的“加载动画”其实是**日志、阶段、产物、控制按钮**的组合。

### 2.6 Cursor

可借鉴点：

- Cloud Agents 支持**并行执行**，并强调不需要笔记本一直在线；
- Cursor 3 把长任务可视化为统一 workspace；
- Cloud agents 会产出 **demos 和 screenshots** 供验证；
- 支持本地与云端 agent 的**快速切换与接力**。

启发：

- 对复杂任务，最好的加载反馈不是图形抽象，而是**“已生成了哪些可检查的中间成果”**；
- 后台任务 UI 应支持：
  - 活跃任务列表；
  - 当前阶段；
  - 最近产出；
  - 可切回前台接管。

## 3. 从这些产品里抽出来的 9 个共性原则

### 原则 1：不要把长任务伪装成普通 loading

`spinner + “正在思考”` 只适合 1–5 秒。  
超过 8–10 秒后，用户已经不再期待“快返回”，而是在判断：

- 是不是卡住了；
- 我还能不能切走；
- 它到底在做什么。

所以超过阈值后，必须从 **loading 态**切换到 **task 态**。

### 原则 2：先给计划，再给执行

长任务最容易建立信任的方式，是先让用户看到：

- 任务理解；
- 执行范围；
- 计划步骤；
- 允许修改的点。

这样用户会觉得 AI 不是“闷头跑”，而是“按我同意的方向跑”。

### 原则 3：动画要绑定真实事件，不要纯装饰

真正能降低焦虑的不是 motion 本身，而是 motion 对应的**真实工作证据**：

- 找到新来源；
- 完成一个阶段；
- 生成了大纲；
- 执行了一个工具；
- 产出了一张图、一段 diff、一个草稿。

### 原则 4：对长任务要允许离开当前页面

长任务如果要求用户盯着主界面看，就是设计错误。  
正确方式是：

- 明确提示可转后台；
- 在侧边栏 / 顶栏 / 任务中心保留状态；
- 完成时通知；
- 返回时可恢复上下文。

### 原则 5：显示阶段，比显示假百分比更重要

对于检索、推理、外部工具执行、联网操作，精确百分比通常并不可信。  
比“64%”更可信的是：

- 已完成：理解任务、制定计划；
- 进行中：读取 18 个来源；
- 下一步：撰写报告并补齐引用。

### 原则 6：不同等待原因，必须用不同视觉语言

至少要区分：

- **积极执行中**；
- **等待外部系统**；
- **等待用户确认**；
- **重试中**；
- **已转后台**；
- **已完成待查看**。

如果所有状态都用同一种旋转动画，用户会误判。

### 原则 7：对高风险任务，要把控制权显式露出来

例如写代码、改文档、跑脚本、调用第三方系统。  
UI 上应露出：

- 停止；
- 调整方向；
- 查看中间结果；
- 回到最近安全点；
- 人工确认继续。

### 原则 8：长任务的核心不是“让用户不烦”，而是“让用户可并行做别的事”

最好的体验不是把用户困在加载页，而是：

- 告诉他可以去做别的；
- 告诉他回来时在哪看结果；
- 告诉他任务不会丢；
- 告诉他什么时候需要回来干预。

### 原则 9：最终交付前，要先给“可审阅态”

不要只显示“已完成”。  
更好的状态是：

- 已生成初稿，等待你审阅；
- 已完成分析，正在准备可视化；
- 已生成方案，建议先预览再发布。

这样会显著提高“过程可信度”和“结果可控感”。

## 4. 不同情景下的 AI 加载动画方案

下面按任务时长和任务性质来拆。

## 4.1 场景 A：1–3 秒，普通问答 / 快速改写 / 简短检索

### 目标

- 让等待显得流畅；
- 避免 UI 抖动；
- 不引入复杂任务感。

### 推荐方案

- 使用**头像呼吸脉冲**或**输入框上方轻微 shimmer**；
- 同时保留**文本骨架屏**，让页面看起来不是空白等待；
- 如果支持流式输出，优先尽早开始吐第一句，而不是先播动画再出字。

### 动画建议

- 呼吸点：`1.2s - 1.6s`，透明度 `0.45 -> 0.9 -> 0.45`；
- 头像或 AI 图标轻微放大缩小：`scale(0.98 -> 1.02)`；
- 骨架屏横向 shimmer 速度慢一些，避免廉价感。

### 文案建议

- `正在组织回答`
- `正在检索关键信息`
- `正在生成可读版本`

### 不要这样做

- 不要上大转圈；
- 不要出现“正在深度思考”这种过重文案；
- 不要把短任务做成任务面板。

---

## 4.2 场景 B：3–15 秒，标准回答 / 轻量多步推理 / 轻搜索

### 目标

- 证明 AI 不是卡死；
- 让用户觉得答案在持续推进；
- 开始建立一点“阶段感”。

### 推荐方案

- 主区域使用**阶段字幕 + 活性动画**；
- 配一个**轻量事件 ticker**，每 1–2 秒更新一句过程短语；
- 若有来源检索，开始显示来源 chip，但不必铺满。

### 视觉结构

- 上：状态 chip，如 `正在分析问题`
- 中：简洁动画（脉冲环 / 扫描线 / 轻轨迹）
- 下：事件文案轮播

### 文案轮播示例

- `识别你的目标`
- `补充相关上下文`
- `交叉整理答案结构`
- `检查表述是否一致`

### 推荐动画

- **脉冲环**：表示系统活着；
- **扫描线**：表示正在搜索 / 遍历；
- **文字渐显**：表示有进度在推进。

### 技术建议

- 优先 `CSS + SVG`；
- 不必上 `Canvas`；
- 所有运动都用 transform / opacity，不做重排。

---

## 4.3 场景 C：15 秒–2 分钟，深度检索 / 多来源对比 / 报告初稿

### 目标

- 把“等待”升级成“能观察的工作流程”；
- 降低“这是不是卡住了”的怀疑；
- 给用户可以干预的时机。

### 推荐方案

切换成 **阶段式任务卡**：

1. 理解任务
2. 制定计划
3. 搜集资料
4. 对比与归纳
5. 撰写输出

### 推荐界面

- 左侧或顶部：阶段轨道（不是精确百分比）
- 中间：当前阶段大卡片
- 右侧或下方：事件流 / 来源流 / 中间产物

### 这时动画的核心不再是“循环播”

而是：

- 阶段切换时有明显过渡；
- 每出现一个来源 / 一个子步骤，就追加一条真实事件；
- 已完成阶段变成静态确认状态。

### 推荐动态元素

#### 1. 阶段轨道

- 当前步骤高亮；
- 已完成步骤实心勾选；
- 未开始步骤弱化；
- 当前步骤不要闪烁，用**缓慢流动高亮**即可。

#### 2. 来源流

- 每出现一个来源 chip，做一次 `fade + slide-up`；
- 可显示来源数：`已读取 18 个来源`；
- 如果有可信来源策略，可显示“已纳入指定站点”。

#### 3. 初稿预告

- 不是等全部完成再出内容；
- 可以先显示：
  - 提纲；
  - 章节标题；
  - 已确定的对比维度。

### 推荐文案

- `已生成研究计划，正在读取来源`
- `正在对比相互矛盾的信息`
- `已完成资料采样，开始撰写初稿`
- `正在补齐引用与出处`

### 用户控制

- `停止`
- `调整重点`
- `限制数据来源`
- `转到后台继续`

---

## 4.4 场景 D：2–10 分钟，Agent 任务 / 调工具 / 写代码 / 跑多步骤自动化

### 目标

- 让用户感觉 AI 像一个“正在工作的同事”；
- 能理解当前任务拆解；
- 能看到中间产物；
- 能放心离开。

### 这时不该再叫“加载动画”

应该设计成 **任务工作台**。

### 推荐工作台结构

#### 第一层：总状态栏

- 任务名；
- 当前阶段；
- 已运行时长；
- 当前子任务数；
- `停止 / 暂停 / 继续 / 调整方向`。

#### 第二层：任务树

例如：

- 需求理解
- 环境准备
- 检索资料
- 生成产物
- 校验
- 收尾

每个节点可以展开看更细步骤。

#### 第三层：证据面板

根据任务类型切换：

- 代码任务：diff、测试结果、截图、日志；
- 数据任务：表格、图表、处理中间文件；
- 文档任务：提纲、段落草稿、引用列表；
- 多模态任务：缩略图、渲染帧、版本记录。

### 推荐动画形态

#### 1. 任务节点流动高亮

表示当前节点正在执行，而不是整个界面乱动。

#### 2. 实时日志增量出现

每条日志使用很轻的 slide-in；
越长的任务，越该靠日志/事件证明活性。

#### 3. 产物缩略图渐进填充

比如：

- 截图先出占位；
- 生成完后替换成实际缩略图；
- 让用户看到“真的产生了东西”。

### 推荐文案

- `正在执行第 3 个子任务：整理引用清单`
- `已完成代码修改，正在运行测试`
- `任务已转后台，不影响你继续使用`
- `已生成可预览草稿，正在补充细节`

### 必备控制

- `查看运行日志`
- `切换到详细模式`
- `仅看产物`
- `停止并保留当前结果`
- `回到最近成功步骤`

---

## 4.5 场景 E：10 分钟以上，报告 / 幻灯片 / 批处理 / 多文件生成

### 目标

- 避免用户被主界面绑住；
- 避免大动画长期占据注意力；
- 把任务从“交互瞬态”变成“异步项目”。

### 推荐方案

使用 **后台任务中心 + 持续通知机制**。

### 核心设计

#### 主界面

只保留一个紧凑状态条：

- `AI 正在后台生成季度汇报`
- `预计仍需数分钟`
- `完成后提醒你`

#### 任务中心

卡片化展示：

- 任务名称；
- 当前阶段；
- 最新更新时间；
- 最近产物；
- 是否需要人工确认；
- 完成后入口。

#### 完成提醒

- 页内 toast；
- 侧边栏已完成标记；
- 移动端 push / 系统通知；
- 回到线程可直接打开结果。

### 动画建议

- 不要再用大面积持续运动；
- 只保留低频活性提示：
  - 每 2–3 秒一次微脉冲；
  - 最新步骤出现时短动画；
  - 完成时强调动画。

### 适合显示的内容

- 已产出文件数；
- 最新产物缩略图；
- 最近一条关键日志；
- 是否卡在外部依赖；
- 下一次需要用户操作的点。

---

## 4.6 场景 F：等待外部系统 / 排队 / 速率限制 / 审批确认

### 目标

- 明确说明“不是卡死，而是被阻塞”；
- 避免继续使用“积极执行中的动效”误导用户；
- 降低无效刷新和重复提交。

### 状态要明确拆开

#### 执行中

- 用扫描、流动、节点推进。

#### 等待外部响应

- 改成**低频闪烁 + 等待标签**；
- 不再使用快速扫描。

#### 等待用户确认

- 改成明显 CTA；
- 动画减弱，把注意力让给按钮。

### 推荐文案

- `已提交外部请求，等待系统返回`
- `当前队列较忙，任务已保留`
- `需要你确认后继续访问该系统`
- `正在重试第 2 次`

### 关键点

- “等待型状态”要让用户知道**可以不用盯着看**；
- 同时保留“上次成功做到哪一步”的信息。

---

## 4.7 场景 G：失败 / 部分成功 / 可恢复失败

### 目标

- 不让用户感到整个任务白做；
- 保留已完成成果；
- 给出恢复路径。

### 推荐方案

失败界面至少展示：

- 最后成功步骤；
- 失败发生在哪一步；
- 是否自动重试过；
- 当前还能保留哪些结果；
- 下一步建议动作。

### 动画建议

- 避免满屏红色震动；
- 用**一次性状态切换动画**即可；
- 重点是信息，而不是情绪化视觉。

### 推荐文案

- `检索阶段已完成，但写作阶段失败`
- `外部来源连接超时，已保留已读取内容`
- `你可以从“撰写初稿”重新开始`

## 5. 给你的推荐落地方案：三层反馈系统

如果你是做自己的 AI 产品，我建议不要设计一套单一 loading，而是设计 **三层反馈系统**。

## 5.1 第一层：Liveness Layer（活性层）

作用：证明系统还活着。

元素：

- AI 头像呼吸；
- 顶部状态点；
- 轻微脉冲环；
- 计时器。

适用：

- 所有任务都需要。

原则：

- 要轻；
- 要持续；
- 不能喧宾夺主。

## 5.2 第二层：Stage Layer（阶段层）

作用：告诉用户做到哪一步了。

元素：

- 阶段轨道；
- 当前步骤标签；
- 子任务树；
- 最近成功步骤。

适用：

- 超过 8–10 秒的任务；
- 有多步骤的任务；
- 任何 agent 任务。

原则：

- 阶段必须稳定，不要频繁改名；
- 阶段数建议 `4–7` 个；
- 不展示不可信的精确百分比。

## 5.3 第三层：Evidence Layer（证据层）

作用：让用户看到 AI 真做了事。

元素：

- 来源 chip；
- 日志流；
- 提纲；
- diff；
- 图表；
- 文件缩略图；
- 中间草稿。

适用：

- 深度检索；
- agent；
- 代码 / 文档 / 数据类任务；
- 10 分钟以上任务。

原则：

- 真实事件优先；
- 产物比动画更能消除焦虑；
- 对复杂任务，证据层的重要性大于视觉层。

---

## 6. 建议的状态机

建议你的前后端统一成下面这套状态：

1. `queued`
2. `understanding`
3. `planning`
4. `executing`
5. `synthesizing`
6. `waiting_external`
7. `waiting_user`
8. `retrying`
9. `backgrounded`
10. `ready_for_review`
11. `completed`
12. `failed`
13. `cancelled`

### 每个状态对应的 UI 表现

#### queued

- 轻脉冲；
- 显示排队原因；
- 可取消。

#### understanding / planning

- 重点显示任务理解与计划生成；
- 可在 planning 阶段允许用户修改范围。

#### executing

- 展示节点推进、日志流、来源或工具事件；
- 是动效最活跃的阶段。

#### synthesizing

- 运动要慢下来；
- 更适合显示提纲和成品结构；
- 让用户感知“不是还在搜，而是在收束”。

#### waiting_external

- 动作明显降速；
- 强调“等待外部系统”，不要伪装成仍在积极计算。

#### waiting_user

- 强 CTA；
- 动画退后。

#### backgrounded

- 主视图只保留紧凑状态条；
- 任务中心持续存在。

#### ready_for_review

- 不是“已结束”，而是“可以看了”；
- 适合做一次完成强调动画。

## 7. 动画组件建议：用什么动效表达什么状态

## 7.1 呼吸脉冲（Breathing Pulse）

最适合表达：

- 系统在线；
- 正常等待；
- 非侵入式后台执行。

不适合表达：

- 高强度扫描；
- 并行复杂工作。

## 7.2 扫描线（Scanning Sweep）

最适合表达：

- 搜索；
- 读取来源；
- 遍历资料。

不适合表达：

- 等待用户确认；
- 已完成待审阅。

## 7.3 阶段轨道流光（Stage Rail Glow）

最适合表达：

- 多步骤长任务；
- 阶段推进；
- 任务仍在向前。

优势：

- 信息密度高；
- 不需要用假百分比。

## 7.4 节点网络 / 粒子网络（Node Graph）

最适合表达：

- 多工具协同；
- 多 agent；
- 多来源汇聚。

注意：

- 只适合产品品牌感强、画面空间足够的场景；
- 如果它不承载真实信息，容易沦为“炫技背景”。

## 7.5 日志流 / 事件流（Activity Feed）

这是最被低估、但最有用的反馈形式。

适合：

- 所有 agent 任务；
- 代码、数据、文档、研究任务；
- 任何超过 20 秒的长任务。

因为它天然回答了用户最关心的三个问题：

- AI 在干嘛？
- 它有没有推进？
- 我现在要不要干预？

## 7.6 产物渐进出现（Artifact Reveal）

适合：

- 幻灯片；
- 文档；
- 图表；
- UI 设计；
- 代码 diff；
- 截图。

原则：

- 先出结构占位，再逐步替换成真实产物；
- 用户看到“东西在出现”，焦虑会明显下降。

## 8. 技术实现建议：动画渲染怎么选

## 8.1 默认优先级

我建议你按下面顺序选：

1. **CSS + SVG**
2. **Canvas（只用于中等复杂动态可视化）**
3. **Lottie（只用于短时品牌动效）**
4. **WebGL / Three.js（除非你的产品把空间感当核心品牌）**

## 8.2 为什么默认用 CSS + SVG

因为它最适合长任务场景：

- 易主题化；
- 易跟状态联动；
- 易做轻量过渡；
- CPU / 电池压力低；
- 可与骨架屏、chip、轨道、图标共用设计语言。

适合做：

- 呼吸脉冲；
- 轨道流光；
- 阶段图标；
- 扫描线；
- 轻量来源出现动画。

## 8.3 什么时候用 Canvas

只有在你需要以下情况时再用：

- 节点网络实时连线；
- 大量粒子轨迹；
- 高频动态背景；
- 复杂波形或流体动画。

但注意：

- 长时间运行的后台任务不适合一直高频绘制；
- 页面失焦后应降帧或暂停；
- 用户开多个任务时，Canvas 动画很容易成为性能瓶颈。

## 8.4 为什么不建议把 Lottie 当主力方案

Lottie 适合：

- onboarding；
- 空状态；
- 一次性成功反馈；
- 品牌过场。

不适合：

- 10 分钟以上持续运行；
- 需要跟真实后台事件一一映射；
- 需要大量变体状态。

根本原因：

- 它更像“预渲染表演”，不是“状态驱动 UI”。

## 8.5 推荐的前后端联动方式

动画不要靠前端自己猜。

最好由后端持续发事件：

```json
{
  "taskId": "task_123",
  "state": "executing",
  "step": "collecting_sources",
  "message": "已读取 18 个来源，正在交叉验证",
  "elapsedMs": 48231,
  "artifacts": [
    { "type": "outline", "id": "outline_1" }
  ]
}
```

推荐事件类型：

- `task_created`
- `plan_ready`
- `step_started`
- `step_completed`
- `source_found`
- `tool_started`
- `tool_finished`
- `artifact_created`
- `waiting_external`
- `waiting_user`
- `retrying`
- `completed`
- `failed`

然后前端只做一件事：

**把每种事件映射成固定视觉反馈。**

## 9. 文案系统建议

长任务场景里，文案和动画同等重要。

## 9.1 好文案的特征

- 是动词驱动，不是空泛形容词；
- 描述当前行为，不描述抽象能力；
- 能说明下一步会发生什么；
- 能告诉用户是否需要操作。

## 9.2 推荐文案模板

### 执行中

- `正在制定研究计划`
- `正在读取指定来源`
- `正在交叉验证冲突信息`
- `正在生成第一版结构`
- `正在运行测试并整理结果`

### 可离开

- `任务已转到后台继续`
- `你现在可以离开，完成后会提醒你`
- `AI 会继续处理，不影响你执行其他操作`

### 等待型

- `正在等待外部系统返回`
- `需要你确认后继续`
- `当前队列较忙，任务已保留`

### 收尾型

- `已完成分析，正在整理输出`
- `初稿已生成，正在补齐引用`
- `已可预览，建议先审阅`

### 失败恢复型

- `已保留前面步骤结果，可从这里继续`
- `外部连接超时，建议重试当前步骤`
- `代码修改已完成，但校验未通过`

## 10. 你这个产品最推荐的具体组合

如果让我直接给一个默认方案，我会建议：

## 10.1 默认组合

### 对 0–8 秒任务

- 头像呼吸脉冲
- 文本骨架屏
- 流式输出尽早开始

### 对 8–90 秒任务

- 阶段轨道
- 当前步骤卡
- 事件流
- 轻量来源 / 工具 chip
- `停止 / 调整方向`

### 对 90 秒以上任务

- 任务工作台
- 背景任务中心
- 产物预览
- 通知机制
- `转后台继续`

## 10.2 视觉风格建议

- 不要做“宇宙星空 + 无限粒子漂浮”这类纯概念动画；
- 更推荐**结构化、工程感、可信赖**的视觉语言：
  - 轨道；
  - 节点；
  - 状态点；
  - 日志；
  - 产物缩略图；
  - 已完成勾选。

因为你的目标不是“看起来像 AI”，而是：

**让用户知道 AI 在认真工作，而且我随时能接管。**

## 10.3 最重要的一条

长任务场景下，真正能降低焦虑的排序通常是：

1. **真实阶段**
2. **真实证据**
3. **可控入口**
4. **后台恢复能力**
5. **动画本身**

也就是说：

如果只能做好一件事，先把**阶段与证据**做好，再做动画。

---

## 11. 不建议做的 8 件事

1. 长时间只放一个 spinner；
2. 给不可信的精确百分比；
3. 外部等待时仍用积极扫描动画；
4. 任务转后台后没有统一入口；
5. 任务完成后没有显式提醒；
6. 失败后不保留中间结果；
7. 所有任务都复用同一套“思考中...”文案；
8. 用高能耗大动画持续跑 10 分钟以上。

---

## 12. 一句话结论

**AI 长任务的最佳加载方案，不是做一个更漂亮的 loading，而是把加载重构成“可观察、可中断、可转后台、可审阅的任务执行界面”。**
